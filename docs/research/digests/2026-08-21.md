## Item 1 — Ollama/XGrammar claim, VERIFIED (resolves iteration 13's flagged risk)

Iteration 13 flagged an unverified search-snippet claim that "Ollama uses
XGrammar under the hood" for constrained decoding, and noted this would be a
real baseline-drift risk for G1's measurements (which assume llama.cpp/
Ollama's own GBNF grammar engine, not XGrammar) if true. This iteration's
next-action explicitly asked for direct verification via Ollama's own
GitHub repo rather than search snippets.

**Verdict: the claim does not hold for Ollama's structured-output mechanism
as implemented.** Fetched Ollama's actual structured-outputs PR
(`ollama/ollama#7900`, "Structured Outputs - Chat Endpoint") directly. The
PR discussion explicitly rejects adopting an external grammar engine:

> "Sampling performance - there are many new papers and methodologies for
> grammars (outlines, xgrammar, etc). We want to keep grammar generation and
> sampling coupled to improve the performance of sampling down the road."

The implementation converts a user-supplied JSON schema to a grammar
internally and keeps grammar generation coupled with sampling — i.e. the
team deliberately did NOT integrate XGrammar, consistent with G1's existing
framing (llama.cpp/Ollama's own GBNF-family engine, not XGrammar). One
caveat worth recording: a WebSearch snippet in the same sweep also surfaced
a contradictory claim ("a stubbed out version of xgrammar was merged, though
there have been some implementation challenges") — this reads as noise from
an unrelated/upstream project, not Ollama's own PR thread, and the primary
source (the actual PR discussion) is unambiguous. **Verdict: differentiate-
from / non-issue.** No baseline-drift action needed. Not entering `seen.json`
as a citable research item (it's an implementation-verification check, not a
paper), but recording the PR URL as checked.

## Item 4 — general mask/grammar sweep, two new items

- **ATLAS-RTC: Closing the Loop on LLM Agent Output with Token-Level Runtime
  Control** (arXiv 2603.27905, new). A closed-loop runtime-control system for
  structured generation: monitors decoding for drift from the output
  contract using lightweight signals, then intervenes with biasing, masking,
  or rollback — instead of static constrained decoding or post-hoc
  validation. Reports first-attempt success rate improvements of 20–37.8pp
  and up to 88% latency reduction "in failure-dominated settings" on
  structured-generation and tool-calling tasks. **Differentiate-from**: this
  is a correctness/reliability mechanism (reduce retries/failures), not a
  hardware-cost-of-masking mechanism — no edge-hardware, Joules, or
  single-stream-forward-pass angle in the abstract. Worth carrying as a
  correctness-tax-cluster-adjacent citation (a different family of fix for a
  related problem: "make constrained decoding not silently produce
  locally-valid-but-wrong output," same spirit as DCCD 2603.03305) and as a
  reminder that "latency reduction via smarter constrained decoding" is an
  active research line, just not one that touches G1/Route A's specific
  claim (the *baseline* per-token mask-walk cost on edge SoCs).
- **Weave of Formal Thought (WoFT)** (arXiv 2606.25987, new). A sound-and-
  complete constrained decoder for **code generation** built against the
  full Tree-sitter grammar specification (context-sensitive lexing,
  maximal-munch tokenization) — a different domain (code, not JSON/medical
  schemas) and a different concern (formal completeness of the mask, not its
  runtime cost). **Ignore** for G1/Route A's purposes — no latency, energy,
  or edge-hardware content in the abstract; noted only because it's another
  data point that constrained-decoding *correctness/completeness* is an
  active line distinct from the *cost* line this work occupies.
