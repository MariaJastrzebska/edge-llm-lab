## Main task: novelty check on Route A's "hero optimization" (shadow-mask pipelining)

Per iter 17's next-action, checked whether anyone has already proposed the
specific mitigation Route A would build — overlapping CPU-side grammar-mask
computation with the GPU's forward pass, syncing only before sampling — as
opposed to the already-tracked *alternative* masking-speedup approaches
(PSC/GRID/Pre³/XGrammar-2, all batch-serving-side).

**Result: this mechanism is not new — and this loop already knew that.**
Rereading `docs/research/digests/2026-08-10-2.md` (iteration 2, the very
first Stage-2 sweep) turned up an entry already on file for **XGrammar**
(arXiv 2411.15100, Nov 2024) stating explicitly: *"the mask is computed on
the CPU in parallel with the GPU's forward pass."* That is the exact
mechanism. XGrammar is not a new find (it's been in `seen.json` since
2026-08-10) and today's re-check didn't change its status — but it's worth
spelling out here because the mechanism-level implication only became
relevant once Route A named "pipeline the mask" as its headline contribution
(2026-08-14, four days after XGrammar was first swept), and STATUS.md's
"Known competitive pressure" section names only **XGrammar-2** as the
tracked cluster member, which risks a reader missing that the *original*
XGrammar — not its 2026 successor — is the one that already does this.
Fixed the ambiguity in STATUS.md this iteration (see below); no new
`NEEDS_INPUT.md` entry, because nothing changed about what's known, only
about how clearly it's written down.

**Why this doesn't kill Route A's mask-pipelining idea (re-confirmed, not
newly discovered):** XGrammar is a separate, alternative grammar engine —
not integrated into llama.cpp (confirmed via GitHub/docs search: "XGrammar
is designed as a more efficient alternative to llama.cpp's native grammar
engine rather than being integrated into it"), and Ollama's own team
explicitly declined to adopt it (confirmed directly against
`ollama/ollama#7900`, iter 14). llama.cpp/Ollama — the actual engine G1
measures — still does *not* pipeline mask computation with the forward pass.
So the open contribution isn't "invent pipelining" (already done,
already known, already cited in this repo since iter 2) but **"port the
already-known technique to llama.cpp and characterize the regime where its
near-zero-overhead assumption breaks."** That regime is not hypothetical:
one of today's new finds (below) gives independent evidence it's real.

**New-to-`seen.json` items found via this check (5):**
1. **"Challenging GPU Dominance: When CPUs Outperform for On-Device LLM
   Inference"** (arXiv 2505.06461) — **cite, directly relevant.** Deploys a
   1B-param model via **llama.cpp on an iPhone 15 Pro** (Maria's exact
   engine, adjacent device class to iPhone 16 Pro/fed-mobile) and finds
   CPU-only (2 threads, F16) beats GPU acceleration: 17 tok/s vs 12.8 tok/s.
   Matters for Route A's design: XGrammar's and the proposed pipelining
   trick's core assumption is "mask on CPU, forward pass on GPU, hide one
   under the other." If small on-device models are *already* running their
   forward pass on CPU (because CPU wins there), the same core competes for
   the same resource as mask computation — pipelining across CPU/GPU doesn't
   help, and the two might need to be pipelined some other way (e.g.
   across CPU cores, or CPU/ANE) or the crossover simply can't be masked
   away by this technique on the smallest models. This is exactly the kind
   of hardware-regime nuance the "characterize where near-zero-overhead
   breaks" framing needs — strengthens Route A's case that this is real
   systems work, not "port and confirm," but it also means the pipelining
   method needs a design answer for the CPU-decode case before being sold
   as the fix, not just for the GPU-decode case.
2. **"Thinking Before Constraining: A Unified Decoding Framework for LLMs"**
   (arXiv 2601.07525, "In-Writing", Nokia Bell Labs) — **cite, correctness-
   tax cluster, fix-side.** Lets the model reason freely, then applies
   constrained decoding only after a trigger token — decouples reasoning
   from formatting to avoid constraints choking off reasoning quality. Same
   spirit as ATLAS-RTC (iter 14): a mitigation for the correctness tax, not
   a hardware-cost paper — no edge/Joules/single-stream angle. Not
   competitive with G1/Route A's hardware-cost claim.
3. **"FairyFuse: Multiplication-Free LLM Inference on CPUs via Fused Ternary
   Kernels"** (arXiv 2604.20913) — **differentiate-from.** Low-level CPU
   kernel optimization (ternary quantization, no multiply ops) — genuinely
   systems-low-level in the same spirit as this work, but a completely
   different mechanism (compute kernels, not grammar masking) and no
   constrained-decoding angle. Worth a related-work sentence as "other
   low-level CPU optimization for on-device LLMs," not a threat.
4. **"Type-Constrained Code Generation with Language Models"** (arXiv
   2504.09246) — **ignore.** Code-generation domain (type systems), not
   grammar/JSON-schema decoding, no edge/latency angle.
5. **"The Alignment Problem in Constrained Code Generation"** (arXiv
   2606.21619) — **ignore.** Same code-gen domain, accuracy/alignment
   framing, no systems angle.
