## Part 1 — Analysis of the overnight pilot (Linux-side read of NIGHT-REPORT.md)

### What ran (not by this loop — found already committed locally, unpushed)
- **002-g1-mask-cost-pilot**: `granite3.1-dense:2b` Q4_K_M, 20 fixed medical
  tool-call prompts × 3 conditions (unconstrained / gbnf / json_schema) × 5
  repeats = 300 runs, all clean (energy-window coverage 1.00, zero failures).
- **003-g1-model-axis**: same design across 4 models (qwen3:4b, phi4-mini,
  granite3.1-dense:2b, gemma3:4b — gemma3:4b's GGUF failed to load on this
  llama.cpp build and was skipped, recorded not faked). 360/360 attempted
  runs ok.
- Both ran on a MacBook Air M1, with a new streaming powermetrics recorder
  built specifically because the existing instantaneous-sampling backend
  can't produce Joules (the metric G1/G2 need). Manifest discipline (git SHA,
  llama.cpp SHA `030ebb5`, model digest, quantization, sampler settings, idle
  baselines) matches BRIEF's paper-grade requirements.

### The result
Per-token decode time, paired by (prompt, seed), gbnf − unconstrained:

| model | paired diff | 95% CI | detection floor |
|---|---|---|---|
| qwen3:4b | **−0.879 ms** | [−1.279, −0.479] | 0.62% |
| phi4-mini | −0.939 ms | [−2.227, +0.349] | 2.13% |
| granite3.1-dense:2b | +0.088 ms | [−0.094, +0.269] | 0.50% |

No model shows a positive latency tax. The one CI that excludes zero
(qwen3) is negative — constrained decode ~1.3% *faster*, opposite to G1's
prediction. This directly contradicts the 3.6–8.2× overhead figures from
parts of the literature (on this hardware/model combo specifically).

### Why this is not a kill (yet)
G1's mechanism is specifically about a *short* GPU forward pass leaving no
room to hide CPU mask-construction behind it. The fastest condition tested
decoded at 36.8 ms/token (granite) — nothing here is close to the regime
where a sub-millisecond mask-walk would even be a meaningful fraction of the
per-token budget. XGrammar's own "<40 µs/token" claim is ~0.1% of a
37–66 ms forward pass; the pilot's best detection floor is 0.50%, i.e. the
instrument is 5–20× too coarse to see that claim either way. **The
experiment measured "does grammar constraint cost anything on this
particular Mac with these particular 2–4B models" (answer: no, or a wash)
— it did not yet measure "what happens when the forward pass is short."**
That second question is what G1 actually bets on, and it's untested.

### Confound flagged in the pilot (now also in CLAUDE.md's known-bugs list)
The unconstrained condition's 1% schema-validity rate is mostly a
**pre-existing repo bug**: `constant_data_en.txt`'s worked example uses
`"status": "INCOMPLETE"` (uppercase) while the Pydantic schema only accepts
lowercase. Unconstrained models faithfully copy the prompt's own bad
example and then fail validation against a schema that example contradicts.
Grammar-constrained conditions are immune by construction (can't emit the
uppercase form), so the resulting ~100× "J per valid output" gap in the raw
numbers substantially measures "constraint masks an asset bug," not
"unconstrained decoding is unreliable." Appended to CLAUDE.md's known-bugs
section per the report's request; not fixed here (would break comparability
with already-run 003, and fixing it is a code change outside this loop's
`docs/research/`-only scope this iteration).

A second artifact: qwen3:4b hit the 768-token cap in 60/60 unconstrained
runs (it reasons in prose before ever reaching JSON), so its energy number
is "cost of burning the whole budget," not "cost of an answer" — the
apparent 44% energy saving from constraining qwen3 is not a real saving,
it's censored data.

### What a real falsification test of G1 needs
A model/hardware combo that actually decodes fast enough to enter the
short-forward-pass regime — a much smaller model (sub-1B) and/or hardware
with a faster memory path relative to CPU mask-walk cost. Whether that's a
smaller model on the same Mac, or genuinely different hardware (Pi 5,
Jetson, iPhone), is a scope/spend decision, not a research-literature
question — hence [NEEDS-INPUT] rather than another autonomous sweep.

## Part 2 — Literature scoop-check on G1 (11 new sources, ~10 queries)

Run to make sure nothing in the four months since the last sweep has
already published the thing G1 would become. Nothing here changes the
pilot analysis above; it's the originally-planned Stage-3 prep, kept
because it's still valid input for whatever G1's next form turns out to be.

- **PSC: Efficient Grammar-Constrained Decoding via Parser Stack
  Classification** — https://openreview.net/forum?id=SEjxNfQTHN
  Computes vocab masks via a precomputed parser-stack classifier, up to
  770× faster than baselines on complex grammars. **Verdict:
  differentiate-from, track as erosion risk.** Attacks the *cost of
  computing* the mask (algorithmic), not the *overlap failure* G1 is about
  (systems: CPU↔GPU sync on a shared bus). If mask computation gets cheap
  enough, there's less to hide in the first place — shrinks G1's ceiling
  effect size without eliminating the sync-stall mechanism itself. Would
  upgrade to a kill if someone measures PSC-style masking *with pipelining*
  on unified-memory edge hardware in Joules.
- **Flexible and Efficient Grammar-Constrained Decoding** —
  https://arxiv.org/abs/2502.05111 — foundational precursor to PSC/XGrammar
  lineage. **Verdict: cite** as background.
- **LLM Inference at the Edge: Mobile, NPU, and GPU Trade-offs Under
  Sustained Load** — https://arxiv.org/html/2603.23640v1 — thermal
  dissipation, not peak compute, binds sustained mobile inference.
  **Verdict: cite** — motivating context, and a caution: the overnight
  pilot's runs were not checked for thermal throttling drift beyond the
  idle-baseline-before/after control, worth tightening in any follow-up.
- **MELTing Point: Mobile Evaluation of Language Transformers** —
  https://arxiv.org/pdf/2403.12844 — established mWh/token as a
  measurement convention on Jetson-class devices. **Verdict: cite** —
  methodology precedent.
- **Mitigating Bias in Locally Constrained Decoding via Tractable
  Proposals** — https://arxiv.org/pdf/2606.01926. **Verdict: ignore** —
  correctness/bias framing, not performance/energy.
- **Constrained Decoding for Diffusion Language Models** —
  https://arxiv.org/pdf/2607.07026. **Verdict: ignore (differentiate)** —
  different decode paradigm, outside llama.cpp's autoregressive scope.
- **Towards Multi-Model LLM Schedulers: Offloading and Preemption** —
  https://arxiv.org/html/2605.19593v1. **Verdict: ignore** —
  scheduler-level, different mechanism altitude.
- **T-SAR: Full-Stack Co-design for CPU-Only Ternary LLM Inference** —
  https://arxiv.org/pdf/2511.13676. **Verdict: ignore** —
  quantization/kernel angle, orthogonal to grammar masking.
- **Edge-Based QoS-Aware Adaptive Task Placement: Multi-Robot Systems** —
  https://arxiv.org/pdf/2606.00552. **Verdict: ignore for G1, weak-cite for
  the robotics-framing angle** — task-placement layer, not LLM decode.
- **SafeDec project page** — https://constrained-robot-fms.github.io/
  (arXiv 2509.01728 already logged). New detail: SafeDec enforces safety by
  *simulating candidate actions* against STL, a different mechanism
  (trajectory simulation) than vocabulary masking. **Verdict: cite** —
  keeps the robotics-framing angle differentiated if G1 survives in some
  form.
- **MLSys deadline trackers** —
  https://mlsys-deadlines.github.io/, https://casys-kaist.github.io/.
  **Verdict: informational.** Both still show MLSys 2027 as TBD/predicted
  off the 2026 Oct 30 date. No change to the deadline table.
