## Item 1 — Format Tax citing-work check, resolved (iteration 14's carried-over task)

Iteration 14 flagged one citing paper, "One Token Away from Collapse: The
Fragility of Instruction-Tuned Helpfulness" (arXiv 2604.13006), but couldn't
confirm its actual argument because `arxiv.org` was blocked. Still blocked
this iteration (`arxiv.org` and `semanticscholar.org` both returned
EGRESS_BLOCKED), so — per iteration 14's own fallback instruction — used a
direct WebSearch quote-check instead of a third arXiv fetch attempt.

**Verdict: not a decoder-level extension of Format Tax — a different
mechanism, only thematically adjacent.** "One Token Away from Collapse"
shows that simple *lexical* constraints (banning a single punctuation
character or common word) cause instruction-tuned LLMs to collapse response
comprehensiveness by 14–48% (GPT-4o-mini: 31% loss), diagnosed as a planning
failure, with two-pass generation (free generation, then constrained
rewriting) recovering 59–96% of lost length. This is about lexical/logit-bias
constraints on *content words*, not schema/CFG grammar masking on
*structural* tokens — a related but distinct fragility story. It does not
appear to make Format Tax's specific prompt-vs-decoder attribution argument
any further. **Closing this open item as "differentiate-from, not a
citing-extension"** rather than carrying it forward again.

## Item 3 — Ollama's own Apple Silicon backend switched from Metal to MLX (Ollama 0.19, March 2026) — NEW, harness-relevant baseline-drift signal

Widened the sweep to the Apple-Silicon-engine baseline-drift watch (last
touched iteration 11/12, per the standing "don't repeat a narrow query two
iterations running" rule). Found something more concrete than the BaseRT/
MetalRT third-party-runtime watch already on file: **Ollama itself** — the
actual tool G1's harness drives, not a third-party alternative — shipped a
backend change on Apple Silicon.

Ollama 0.19 (preview March 30, 2026; general release March 31, 2026)
rebuilt Ollama's Mac inference stack on top of Apple's MLX framework instead
of calling Metal directly, "to take advantage of its unified memory
architecture." Reported effect: roughly 2× decode speed and ~60% faster
prefill on the same hardware (Linux/Windows keep the llama.cpp path
unchanged — Mac-only change).

**Two qualifiers that keep this from being an action item today:**
1. **Hardware gate:** the MLX path requires 32GB+ unified memory; 8GB/16GB
   Macs are explicitly unaffected ("still run the old Metal path with no
   change"). Maria's M1 hardware spec isn't pinned down in this loop's own
   files, but G1's model set (sub-1B models) doesn't need 32GB, so this is
   a real question mark, not a confirmed hit.
2. **Model gate:** at preview, only one architecture is MLX-accelerated —
   Qwen3.5-35B-A3B — none of G1's four tested families (qwen2.5:0.5b,
   qwen3:0.6b, llama3.2:1b, gemma3:1b).

**Verdict: differentiate-from / baseline-drift-risk-to-watch, elevated
slightly above the BaseRT tier** (BaseRT/MetalRT are third-party engines
Maria's harness doesn't use; this is a version-upgrade risk to the actual
tool the harness calls). Not an action item now — neither the hardware nor
model gates are met for G1's own measurements as configured — but this is
the concrete trigger condition for the "rerun sanity-check whenever the
harness's underlying engine is upgraded" note already on file (iteration
11): **if the installed Ollama version on the test machine is ever bumped
past 0.19, or model coverage expands to include a small dense model on
whatever unified-memory floor eventually applies, G1's baseline decode
speeds could shift and should be re-verified before trusting old numbers
against new ones.** Recording the trigger condition explicitly so a future
iteration (or Maria) can check "what Ollama version did 002–006 actually
run on" without re-deriving this from scratch. Not a grammar/constrained-
decoding-masking paper, so still not competitive with G1/Route A's specific
claim.
